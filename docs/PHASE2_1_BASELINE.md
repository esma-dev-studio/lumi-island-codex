## Character findings

- Production GLBs are generated by `scripts/generate_character_glbs.py`.
- The generator builds the body from lofts, sculpted blobs, and curved sweeps.
- Mira measures 7,763 runtime triangles, 9 runtime meshes, 6 materials, and 0 texture bytes.
- The GLB has 12 joints and 9 animation groups.
- The mesh has no UV set or texture atlas.
- Each generated vertex stores one joint with full weight. There is no elbow, knee, shoulder, or hip weight gradient.
- Blender CLI and Blender Python are not available in the current environment.
- ImageGen is available for 2D concept art, but it cannot deliver a production GLB.
- Therefore the current player asset does not pass the Phase 2.1 character gate and must not be described as a finished high-quality character.
- The procedural generator should remain only as a development fixture until an authored Blender GLB is supplied.

## Product findings

### Tutorial

- Starting a new game opens a blocking modal.
- Clicking `歩いてみる` advances from step 1 to step 2 without moving.
- All seven steps advance from button clicks rather than game events.
- The player cannot learn walking, gathering, crafting, placing, and talking through direct play.

### Resource state

- React writes `resourceStates`, but `GameCanvas` does not pass it to the Babylon scene.
- `availableAt` is written to the current play time rather than a future recovery time.
- The scene owns a separate `available/respawnAt` state, so save/load and visuals are disconnected.
- A depleted target is disabled, which removes the whole target instead of leaving a changed visual.

### Activities

- Wood and stone both use `TimingGatheringGame` and the same horizontal timing UI.
- Wood requires only one input, not a 2–3 hit sequence.
- Stone has no crack-choice decision.
- The reward is committed after a result button; the scene and player animation do not share an `ActivityResult`.
- Fishing has waiting and bite phases, but no cast-position choice, fake nibble, or reel phase.

### Easy mode

- Easy mode changes timing windows and fishing reaction time.
- The normal HUD, interaction copy, menu labels, ruby, and button sizes do not consistently change.
- The difference is primarily a badge and timing tolerance.

### Collection

- Discovery IDs and caught fish IDs are saved.
- There is no collection screen, silhouette list, description, location hint, or completion rate.
- Fishing displays `さかな図かんに のせる` even though no collection screen exists.

### Audio

- Every sound is generated at runtime by `OscillatorNode`.
- There are no authored or licensed audio files, category volumes, mute setting, or audio buffer cache.
- Current audio is a prototype and does not pass the sound gate.

### Code and tests

- `src/scenes/LumiScenes.ts` is 1,663 lines.
- `src/ui/LumiIslandApp.tsx` is 1,065 lines.
- `app/globals.css` is 1,876 lines.
- Character, gathering, fishing, save, collision, and placement unit tests exist.
- Playwright is not installed and there is no reproducible browser E2E suite.

## Browser baseline

- Title screen renders.
- New game starts.
- The first tutorial step advances by click without movement.
- The game canvas and HUD render without a visible blocking error.
- Existing manual screenshots cover Phase 2, but they are not generated by an automated E2E run.

## Baseline conclusion

The Phase 2 build is a playable prototype. The highest-impact Phase 2.1 work is to connect world resource state, replace the click-through tutorial, separate the four activities, add the collection screen and meaningful easy mode, split large responsibilities, add real audio assets, and add reproducible Playwright coverage. The authored character gate remains blocked by the absence of a real 3D authoring tool or suitable licensed source GLB.
