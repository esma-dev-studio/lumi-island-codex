## A01 初期所持金だけで主要購入が終わる

- 事象: 初期120ルーメンに対し、レシピ20、森15×3、ヒント10で主要購入合計75。開始直後に全部買えて45残る。
- 再現手順: 新規ゲーム→メニュー→ルーメン欄を開き、順に購入する。
- 根本原因: Phase 2.2で導線確認用の初期値120と高額報酬を残したまま、低価格の用途を追加した。
- ユーザーへの影響: 何を先に選ぶか、集めて買う喜びがない。
- 優先度: P0。
- 修正対象: `EconomyConfig.ts`、依頼報酬、初期状態、購入処理。
- テスト方法: 初期残高、全価格、購入可否、残高、3ケース試算を単体/E2Eで確認。
- 完了条件: 初期状態で全購入不能。10〜15分で最初、15〜30分で次の意味ある購入が狙える。

## A02 解放が表示物だけで遊びを増やさない

- 事象: 図鑑50%はデッキ、75%は光る庭、島ランク2は橋を表示するだけ。新しい魚・採取・行動条件がない。
- 再現手順: 対応フラグを持つセーブで3D表示とResource定義を比較する。
- 根本原因: `EnvironmentBuilder`の表示切替とResource/Activityの接続が分離していた。
- ユーザーへの影響: がんばっても新しい遊びがなく、報酬が空約束に見える。
- 優先度: P0。
- 修正対象: Unlock/FishingSpot/NightGarden/Resource定義とシーン同期。
- テスト方法: 解放前後のInteractable、魚種、時間条件、セーブ復元を確認。
- 完了条件: 橋、新釣り場、夜の庭、森の各解放で見た目と実際の行動が増える。

## A03 日替わり目標が初期依頼の裏で進む

- ユーザーへの影響: 見ていない目標が突然終わり、報酬理由が分からない。
- 優先度: P0。
- 修正対象: `DailyGoalSystem.ts`、`gameState.ts`。
- テスト方法: 初期依頼中は0、全依頼完了の翌日からのみ加算されることを確認。
- 完了条件: 初期依頼と競合せず、一度に短い1目標だけ表示される。

## A06 タッチ方向パッドが二重入力する可能性

- 事象: 各方向ボタンがpointerdown/upに加えてclickで`tapGameKey`を送る。
- 再現手順: タッチ端末で押して離し、キーイベント列と移動距離を見る。
- 根本原因: クリック操作のフォールバックを押下継続操作へ重ねた。
- ユーザーへの影響: 指を離した後に余計な一歩が出る可能性がある。
- 優先度: P0。
- 修正対象: `TouchMovementController.ts`、`GameHud.tsx`。
- テスト方法: touch emulationでdown/up/cancel/leave/blur後の押下状態と位置を確認。
- 完了条件: 一組のpointerイベントだけで移動し、全終了経路でキーが解除される。

## A07 親密度が会話連打防止付きの数値だけ

- ユーザーへの影響: 関係が深まった実感がない。

- テスト方法: 各段階の条件、会話、レシピ、配置、思い出イベントを確認。
- 完了条件: ノラの3段階で会話と遊びが変わり、同じ会話連打では上がらない。

## A09 完全E2Eと既存E2Eの信頼性が不足

- 事象: チュートリアルE2Eは複数箇所でlocalStorage seedを使い、今回の基準全実行は10成功・1失敗・4未実行。
- 再現手順: `npm run test:e2e`。
- 根本原因: 長い導線を分割seedへ依存し、最初のsuite失敗でserial後続が止まる。
- ユーザーへの影響: 新規ゲームの実導線が壊れても見逃し得る。
- 優先度: P1。
- 修正対象: Phase 2.3完全E2E、待機条件、suite構成。
- テスト方法: localStorage書き込みを禁止した一本を新規ゲームから再読込まで通す。
- 完了条件: 完全導線と追加テストが成功し、未実行数を明記する。

## A10 Validator状態の型が二値

- 事象: 証跡は`passed: boolean`で、実行不能とアセット不合格を明確に別型として表せない。
- 再現手順: Validator依存を外した環境と、実行できる不合格GLBを比較する。
- 根本原因: ツール実行状態とアセット合否を同じbooleanへ畳んだ。
- ユーザーへの影響: 環境障害をアセット欠陥として数える危険がある。
- 優先度: P1。
- 修正対象: validator JSON schemaと自動レポート。
- テスト方法: `passed` / `failed` / `unavailable`の3状態テスト。
- 完了条件: 実行不能はerror件数へ加算せず理由を別記する。

## A11 初回ロードチャンクが大きい

- 事象: 最大クライアントJSは5,471,685 bytes。現ビルドのクライアントassets総量は約7.43MB。
- 再現手順: 本番ビルド後、同一時刻に生成された`dist/client/assets`を集計する。
- 根本原因: Babylon.jsのbarrel importとCharacterView共有チャンクが広いモジュール群を含む。
- ユーザーへの影響: 学校PCや低速回線で初回操作開始が遅い。
- 優先度: P1。
- 修正対象: Babylon deep import、パネル遅延読込、自動計測。
- テスト方法: ビルド成果物、通常/低速条件の初回表示・操作可能時間・FPSを計測。
- 完了条件: 最大チャンクを実測で縮小し、環境と未測定項目を明記する。
